법인카드만 해당되는걸까? 급여도 지급했다가 오지급으로 입금받고 재지급하고 했었거든"(원칙43).
"고정비 항목별 계획 대비 실적" 카드와 "N월 상세" 팝업 모두 같은 유형명의 출금만 더하고 입금

상세팝업 입금 섹션에는 회수분을 "(입금, 참고)"로 계속 표시해 사실 자체는 숨기지 않음.

## v2.9.55 — "N월 상세" 팝업의 원래 목적 회복
사용자 지적: "법인카드가 두번 나오는거도 오류인거 같고, 이 보고서가 보여주려고 했던 양식
목표가 사라진 듯 해" → "그걸 설계하는게 너의 전문 영역이자나"(원칙42). v2.9.54가 8개 고정
버킷을 없애면서 이 팝업을 단순 실적 나열로 바꿔, "추정과 실적의 차이를 설명한다"는 원래

항목은 계획(planFix) 대비 실적으로 비교 표시하도록 재설계하고, 입금·출금 섹션을 명확히
분리해 같은 유형명(법인카드)이 양쪽에 있어도 "(입금)"/"(출금)" 라벨로 구분되게 함.

## 왜 만들었나
이 시스템은 결함을 고칠 때마다 즉석 스크립트로 검증하고 버리는 방식이었다. 그 결과 같은 영역을
다시 건드릴 때마다 검증 코드를 처음부터 새로 짜야 했고, "고쳤는데 다른 게 깨졌다"는 사고가
반복됐다. 이 스위트는 지금까지 실제로 발생했던 결함 전부를 재현 가능한 테스트로 고정해,
앞으로 뭔가 고칠 때 "기존이 안 깨졌는지"를 30초 안에 확인할 수 있게 하는 것이 목적이다.

## 구조
- `calc_*.js` — 순수 함수 계층(schema.js·common.js·calc.js)만 vm으로 로드해 검증. DOM 없이 빠름.
- `e2e_*.js` — 실제 화면(HTML)을 jsdom으로 띄워 클릭·입력 이벤트까지 재현. 느리지만 화면 조작
  순서에서만 드러나는 결함(체크박스 상태 꼬임 등)은 이 방식이 아니면 못 잡는다.
- `_helpers.js`, `_e2e_helpers.js` — 공용 유틸(테스트 파일로 취급 안 됨, run_all.js가 스킵).
- `run_all.js` — 전체 실행기.
- `PRINCIPLES.md` — 이 결함들에서 뽑아낸, 프로젝트에 종속되지 않는 일반 원칙(스킬화 재료).

## 새 결함을 고칠 때 반드시 할 것
1. `node tests/run_all.js`로 기존이 안 깨졌는지 먼저 확인
2. 고친 결함을 검증했던 스크립트를 버리지 말고, 해당 영역의 `tests/*.js` 파일에 케이스로 추가
   (새 화면/새 영역이면 새 파일 생성 — `calc_*` 또는 `e2e_*` 명명 규칙 따를 것)
3. 다시 `node tests/run_all.js`로 전체 재확인
4. zip 패키징 시 `tests/` 디렉토리 전체를 포함할 것(다음 세션·다음 사람이 이어받을 수 있게)

## S12.buy_price의 "단가" 계약(v2.9.26~31)에 대한 메모 — 중요
S12_ESTIMATE.buy_price는 **급여형만 예외**(월별 확정 총액을 memo의 JSON으로 관리)이고, **세금계산서형·
사업소득형은 항상 "단가"**다 — project.html·cashflow.html·input.html의 monthlyProfile이 전부 이
전제로 mm을 곱한다. v2.9.26에서 사업소득형의 이중계산을 막으려 이 필드에 "총액"을 넣는 방향으로
바꿨다가, 그 필드를 읽는 다른 3개 화면과 계약이 어긋나 정확히 mm배만큼 원가가 부풀려지는 결함이
발생했다(v2.9.31에서 발견·원상복구, PRINCIPLES.md 20번). buy_price를 다루는 코드를 또 고칠 일이
생기면, 반드시 이 계약("급여형만 총액, 나머지는 단가")을 먼저 확인하고 project.html·cashflow.html·
input.html 세 곳 모두에 영향이 없는지 점검할 것 — e2e_project_buyprice.js가 이 계약의 감시용이다.
